## 2. 基本設計

AIにプロンプトとしてそのまま渡してコード生成させられるよう、**画面設計・DB設計・API設計**の3つの軸で定義します。

### 2.1 画面設計（画面一覧と遷移）

2人で画面単位の役割分担がしやすいよう、画面構成はシンプルに3画面（またはモーダル構成）とします。

1. **店舗一覧・検索画面（ホーム画面）**
   - **役割:** アプリを開いた最初の画面。検索バー、ステータスタブ（「すべて」「行きたい」「行った」）、エリア・ジャンルのフィルタ、店舗カードのグリッド一覧を表示する。
   - **操作:**
     - 検索条件を変更すると、リアルタイム（または検索ボタン押下）で一覧が絞り込まれる。
     - 「＋お店を登録」ボタンを押すと、**店舗登録・編集画面**へ遷移する。
     - 店舗カードをクリックすると、**店舗詳細・レビュー画面**へ遷移する。

2. **店舗詳細・レビュー画面**
   - **役割:** 選択した店舗のすべての情報（URL、メモ、大きな写真、5段階評価、登録者など）を表示する画面。
   - **操作:**
     - 「行きたい」ステータスの場合、「行った！に変更してレビューを書く」ボタンを目立たせて表示する。
     - 「編集」ボタンで**店舗登録・編集画面**へ遷移。「削除」ボタンで確認後に削除処理を実行し、一覧画面へ戻る。

3. **店舗登録・編集画面（またはモーダル）**
   - **役割:** 新規登録、および既存データの更新を行うフォーム画面。
   - **操作:**
     - ステータスで「行った」を選択した場合のみ、フォーム下部に「評価（★1〜5）」「訪問日」「一言メモ」「写真」の入力欄が展開されるUIとする。

### 2.2 データベース設計（テーブル定義）

最初はリレーション（複数テーブルの結合）を複雑にしすぎず、1つのメインテーブル（`shops`）で完結させる設計にすると、開発スピードが劇的に上がります。

#### テーブル名：`shops`（店舗・ログ情報）

| カラム名 (物理名) | 論理名          | データ型     | 必須 (NOT NULL) | 説明・制約など                                            |
| :---------------- | :-------------- | :----------- | :-------------: | :-------------------------------------------------------- |
| `id`              | 店舗ID          | UUID / INT   |        ○        | 主キー（自動採番）                                        |
| `name`            | 店名            | VARCHAR(100) |        ○        | 例：「〇〇珈琲店」                                        |
| `area`            | エリア          | VARCHAR(50)  |        ○        | 例：「清澄白河」「新宿」など駅名・地域名                  |
| `genre`           | ジャンル        | VARCHAR(50)  |        ○        | 例：「カフェ」「ラーメン」「居酒屋」「イタリアン」        |
| `status`          | ステータス      | VARCHAR(20)  |        ○        | `'want_to_go'`（行きたい） または `'visited'`（行った）   |
| `map_url`         | マップ・参考URL | TEXT         |        -        | Googleマップや食べログ等のURL                             |
| `rating`          | 評価            | INT          |        -        | `1` 〜 `5` の整数（「行った」場合のみ入力）               |
| `memo`            | 一言メモ・感想  | TEXT         |        -        | 気になるメニューや、実際に行った感想                      |
| `image_url`       | 写真URL         | TEXT         |        -        | 料理や外観の画像パス（初期はURL文字列またはローカルパス） |
| `visited_at`      | 訪問日          | DATE         |        -        | 実際にお店に行った日付                                    |
| `created_by`      | 登録者          | VARCHAR(50)  |        ○        | 2人のうちのどちらが登録したか（例：`'UserA'`, `'UserB'`） |
| `created_at`      | 登録日時        | TIMESTAMP    |        ○        | レコード作成日時（デフォルト現在時刻）                    |
| `updated_at`      | 更新日時        | TIMESTAMP    |        ○        | レコード更新日時                                          |

### 2.3 API設計（REST API インターフェース）

フロントエンドとバックエンドを分離して開発する場合（またはNext.js等のAPI Routesを使う場合）、以下の5つのエンドポイントを定義しておくと、2人で並行して作業できます。

| メソッド   | エンドポイント   | 役割                     | クエリパラメータ / リクエストボディ例                                                                 |
| :--------- | :--------------- | :----------------------- | :---------------------------------------------------------------------------------------------------- |
| **GET**    | `/api/shops`     | 店舗一覧の取得・検索     | `?status=want_to_go&area=清澄白河&genre=カフェ&keyword=コーヒー`                                      |
| **GET**    | `/api/shops/:id` | 店舗詳細の取得           | なし（URLの `:id` で指定）                                                                            |
| **POST**   | `/api/shops`     | 店舗の新規登録           | Body: `{ "name": "...", "area": "...", "genre": "...", "status": "want_to_go", "created_by": "..." }` |
| **PUT**    | `/api/shops/:id` | 店舗情報・レビューの更新 | Body: `{ "status": "visited", "rating": 5, "memo": "ラテが最高だった", "visited_at": "2026-10-17" }`  |
| **DELETE** | `/api/shops/:id` | 店舗の削除               | なし（URLの `:id` で指定）                                                                            |
